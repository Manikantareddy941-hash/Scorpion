## 1. Repairs applied in this pass

All five were compiled and tested; the full suite is green after them.

### 1.1 `middleware/iamMiddleware.ts` — authorization failed OPEN (highest severity)

`resolveIamStatements` had the exact bug class the signing work was created to
kill: **a check that could not be performed was treated as a check that passed.**

Two paths, both returning a *grant*:

1. **Unparseable policy document.** A team whose `policy` field existed but did
   not parse fell through to `['admin','owner'].includes(userRole) ? ADMIN_IAM_POLICY : DEFAULT_IAM_POLICY`.
   So corrupting a team's policy blob **escalated** an admin/owner to
   `ADMIN_IAM_POLICY` — unrestricted. The stricter the team's real policy was,
   the more a malformed one granted. Write garbage into one field, get full
   admin. There was no test on this path.
2. **Policy store unreachable.** Any Appwrite/network/quota failure was caught,
   logged at `warn`, and resolved to `DEFAULT_IAM_POLICY` — still a grant. An
   outage silently re-authorized every request against a policy nobody had
   consulted, and said so in a log line nobody greps.

**Now:** both deny. Two distinct error types so the response tells an operator
which system to fix — `IamPolicyUnreadableError` → **403** ("fix the data"),
`IamPolicyUnavailableError` → **503** ("fix the policy store"), both logged at
`error` with userId / action / resourceId / teamId. Same reasoning as
`IMAGE_SIGNATURE_REFUTED` vs `IMAGE_SIGNATURE_UNVERIFIABLE`.

Three tests added covering both denials plus the `hasPermission` path.

### 1.2 `queues/redisConnection.ts` — silent localhost fallback in production

`REDIS_URL || 'redis://localhost:6379'`. Every queue in `src/queues/` (scan,
canary, dast, nuclei, ffuf, report, soar, correlation) and imageStore's
signature/provenance lookups ride this connection. On a hosted container an
unset `REDIS_URL` resolved to nothing at all — and the failure mode is not an
error, it is **accepting jobs no worker will ever read.** A quiet system, not a
broken one. Now throws at module load in production; still defaults (with a
warning) outside it.

### 1.3 `services/dashboardService.ts` — unbounded cache

`dashboardCache` had a 60s TTL that decided whether an entry was *served* but
never removed one. Ceiling was "every user who has ever loaded the dashboard,"
each holding a full stats object for the process lifetime. Now swept on write and
capped at 500 entries.

### 1.4 `runtime/falcoHandler.ts:120` — swallowed owner lookup

`catch (e) {}` on the repo-owner lookup left `ownerUserId` undefined, which
silently drops routing for a **runtime** security alert: recorded, never
delivered to a human. Now logged at `error` naming the un-routed state. Kept
non-fatal so the event still stores.

### 1.5 Test coverage

`iamMiddleware.test.ts` +3 tests (1447 → 1450).

## 2. Confirmed findings NOT repaired — each needs a decision, not a diff

### 2.1 `src/build/buildService.ts` has zero tests and duplicates the primary path

`src/build/` contains exactly one file and **no test file at all**
(`jest src/build` matches nothing). The rethrow that decides whether a broken
signer fails your builds is uncovered. It duplicates `services/pipelineService.ts`,
which is the primary path — and today's entire bug class came from duplicated
security logic drifting apart. **Delete it or cover it. A ticket is not a third
option.**

### 2.2 Seven real circular dependencies

`madge --circular` over `src/` finds 10; three are generated Prisma code. The
other seven are hand-written, and six share one shape — the repository facade
imports its Postgres adapter *and* the adapter imports back:

```
repositories/threatModelRepository.ts  <->  repositories/pg/threatModelPgRepository.ts
repositories/gateRulesRepository.ts    <->  repositories/pg/gateRulesPgRepository.ts
repositories/soarRepository.ts         <->  repositories/pg/soarPgRepository.ts
repositories/postureRepository.ts      <->  repositories/pg/posturePgRepository.ts
repositories/gateRunRepository.ts      <->  services/securityRequirementsService.ts
gitops/canaryService.ts                <->  queues/canaryQueue.ts
repositories/driftRepository.ts -> driftShared.ts -> workers/driftMonitor.ts
```

This is the Phase 1 "strictly decoupled adapters" requirement failing. The fix is
a shared types/contract module the facade and adapter both import, rather than
each other.

### 2.3 Docker images are not pinned to the lockfile — **RESOLVED, with one defect in the fix**

> **Superseded 2026-08-03, later the same day.** `backend/Dockerfile` and
> `backend/package-lock.json` were both changed *during* this audit (they were
> clean at the §0 status check and `M` an hour later, still uncommitted). Both
> stages now use `npm ci`, and the lockfile was regenerated in sync, so plain
> `npm ci --ignore-scripts` resolves cleanly — no `--legacy-peer-deps` needed.
> Verified against the on-disk lockfile in a clean directory. The finding below
> describes the committed state and is retained for history.
>
> **Defect in the fix (`Dockerfile:55-59`).** `--omit=peer` is a no-op here and
> its comment is false. Measured against the real lockfile:
>
> | Command | Packages resolved |
> |---|---|
> | `npm ci --omit=dev` | 1166 |
> | `npm ci --omit=dev --omit=peer` | 1166 |
>
> `react`, `react-dom` and `scheduler` are **still installed in the production
> tree** with both flags set. The comment claims the flag "keeps react/react-dom/
> scheduler out"; it does not. This is the same anti-pattern as §2.6's
> `buildService.ts:174` — a comment asserting a property nothing verifies. Either
> drop `--omit=peer` and the comment, or find the real reason react is in a
> backend image and remove it at the source.
>
> **Also unverified:** the regenerated lockfile has never had the test suite run
> against it. The 1450-passing result in §0 predates it. `npm audit` against the
> new lock is unchanged (1 HIGH picomatch, 0 critical) — I checked that much —
> but `jest` has not been re-run on the new tree.



Both Dockerfile stages use `npm install`, never `npm ci`:

- builder: `RUN npm install --ignore-scripts`
- production: `RUN SCORPION_REQUIRE_TOOLS=1 npm install --only=production`

CI installs with `npm ci --ignore-scripts --legacy-peer-deps`. So **the image
ships a dependency tree that CI never resolved, never tested, and never scanned**
— npm re-resolves from `package.json` and rewrites the lock inside the container.
For a supply-chain security product this is the wrong default. Use
`npm ci --ignore-scripts --legacy-peer-deps` in the builder and
`npm ci --omit=dev` in the production stage.

Related: `--only=production` is a deprecated npm flag. Prefer `--omit=dev`.

Also note the lockfile only installs with `--legacy-peer-deps` — a real peer
conflict (via `prisma` → `@prisma/studio-core` → React 19) is being suppressed
rather than resolved. Harmless today because `prisma` is a devDependency, but it
is why plain `npm ci` fails.

### 2.4 IAM decisions are absent from the tamper-audit trail

`logSecureAuditEvent` is emitted from six modules (`deploy/deployService`,
`routes/remediate`, `services/gateService`, `services/runner/kubernetesRunner`,
`services/threatsService`, `workers/dastWorkerRunner`). **`iamMiddleware` is not
one of them.** Phase 4 requires every access-granted/denied decision to emit an
immutable entry; IAM denials reach the winston logger only. The 403/503 denials
added in §1.1 inherit that gap.

### 2.5 `scorpion_signing_config_broken` is a metric nobody reads

`prometheus.yml` has `scrape_configs` only — **no `rule_files`, no `alerting`
block, no Alertmanager**, and no `*rules*.yml` anywhere in the repo. The gauge
set by the boot probe is scraped and discarded. Until this lands in the external
monitoring config, a host that cannot sign is invisible:

```yaml
- alert: ScorpionSigningConfigBroken
  expr: max by (instance) (scorpion_signing_config_broken) == 1
  for: 10m
  labels: { severity: page }
  annotations:
    summary: "Signing configured but unusable on {{ $labels.instance }} — all signing builds will fail"
```

### 2.6 Provenance is still a write-only facade

`verifyProvenance` and `imageStore.getProvenance` have no callers outside their
own tests. Builds sign SLSA statements into Redis on a 1h TTL and nothing reads
them back. Signing without a read path is theater. Relatedly,
`buildService.ts:174` still carries the claim *"Safe today because provenance is
signed and verified rather than trusted by key"* — **nothing verifies it.** Fix
the comment or delete the file (see §2.1).

### 2.7 `k8sAdmission.checkImageSignature` is structurally correct but dormant

Returns `ready` unless `REQUIRE_IMAGE_SIGNATURE === 'true'` **and** `env === 'prod'`.
Inside the gate it is properly fail-closed (no digest → block, no signature →
block, verify throws → block). Nothing is wrong with the code; it is simply off.
Flipping it is an operator decision that has not been made.

### 2.8 `statusTelemetry` prune has exactly one caller

`store` is bounded to 500 keys *per minute bucket*, but the number of minute
buckets is bounded only by `statusTelemetry.prune()`, called from
`queues/correlationQueueWorker.ts:41`. If the correlation worker is not running,
the map grows for the process lifetime. Slow leak, not a hot one.

### 2.9 `services/scanService.ts:475–483` — three nested empty catches

In the language-statistics walker. Not security-critical on its face, but the
outermost `catch {}` on `readdirSync` means an unreadable scan path yields
`totalFiles: 0` and `detectedLanguage: 'Unknown'` **silently** — and a scan that
covered zero files produces zero findings, which reads as clean. Worth a log line
and an explicit "scanned nothing" signal.

## 5. Addendum — `9bb8673` terminal command surface

Audited after the fact, because this commit landed *during* the audit. HEAD moved
twice in one session (`cfc972c` → `0c0c070` → `9bb8673`), which is the real finding
in §5.5 below.

### 5.1 The security model holds — verified, not taken on trust

- **No `eval`, no `child_process`, no shell.** Confirmed by inspection across
  `services/terminal/` and `routes/terminalRoutes.ts`. The registry `Map.get(verb)`
  miss throws; there is no `default:` branch and no passthrough.
- **Role resolution fails closed.** `resolveRole` has no internal `catch`, so a
  ROLES outage propagates and the route returns **503**, refusing the command.
  This is the pattern §1.1 had to retrofit into `iamMiddleware` — here it was
  right the first time.
- **All three builtins are read-only** and declare `maxArgs: 0`.
- **Rate limited** at 60/min, sized against ledger write volume.
- **24 dispatcher tests pass.**

### 5.2 The audit record stores the input, not the decision

`recordAudit(ctx, raw, outcome)` writes the **raw input string**. The dispatcher
has already computed the authoritative interpretation and even returns it —
`DispatchResult.command` — and that value is discarded.

So the evidentiary record describes what was *typed*, not what *ran*. Two inputs
that render identically can tokenise differently, and one that renders as a
pipeline can tokenise as a bare verb (which is precisely the confusion `maxArgs`
was added to address at the response layer, but not at the ledger layer). For a
hash-chained ledger whose only job is being the record of a decision, log both:
`raw` for forensics, plus the resolved verb and argv for what actually executed.

### 5.3 The fail-open audit write is guarded by a comment, not the type system

`recordAudit` catches and logs `terminal_audit_degraded`. Both the code comment
and the commit message state the constraint clearly and in capitals: this is
defensible only while every verb is read-only, and *"THE MOMENT A MUTATING VERB IS
REGISTERED, this must become fail-closed."*

Nothing enforces it. `register()` accepts any `TerminalCommand`; a future
`register({ name: 'gate override', ... })` silently inherits the fail-open.

This is structurally identical to §2.1 (`buildService.ts`) — a security property
held in place by prose. Cheap fix: make `mutating: boolean` a **required** field
on `TerminalCommand`, and have `recordAudit` rethrow when
`mutating && auditWriteFailed`. The type system then forces the decision at
registration time instead of relying on the next author reading a comment.

### 5.4 `assertPrintable` is ASCII-only — and a hypothesis that mostly did not reproduce

`assertPrintable` rejects `code < 0x20 || code === 0x7f`, i.e. ASCII C0 + DEL
only. It does not reject C1 controls, bidi overrides (U+202A–U+202E), isolates
(U+2066–U+2069), U+2028/U+2029, or U+FEFF — despite the comment stating that
neither an API client nor the ledger "should ever receive a terminal escape
sequence."

I probed for a Trojan Source–style attack on the ledger. **It largely does not
reproduce, for a reason worth recording:**

| Probe | Outcome | Why |
|---|---|---|
| U+202E RLO, U+200E LRM, U+2066 LRI, U+0085 NEL | **rejected** | Character stays inside the verb token → registry miss. Defense in depth working as designed. |
| U+2028 LINE SEPARATOR, U+FEFF ZWNBSP | **accepted** | JS `\s` matches both, so `tokenize` consumes them as delimiters and the clean verb runs. |
| U+0009 TAB | rejected | Caught by `assertPrintable`. |

Residual exposure today is close to nil, because every builtin is `maxArgs: 0` —
anything after the exotic whitespace becomes an argument and is refused. It stops
being nil for the first verb that accepts arguments, where the ledger's `raw`
string will contain separators that do not render as separators. Tighten
`assertPrintable` to a Unicode-category check, and fix §5.2, and this closes.

### 5.5 `terminalRoutes.ts` has zero tests

`commands.test.ts` covers the dispatcher well. The **route** does not: the 503
fail-closed role path, the audit write, and the `CommandError` → status mapping
are all uncovered. Same shape as §2.1 — the dispatcher logic is tested and the
security-relevant glue around it is not.

### 5.6 The process finding, which outranks all of the above

A point-in-time manifest cannot describe a tree that is committed to faster than
it is audited. `RELEASE_MANIFEST_2026-08-03.json` was stale within the hour, and
re-auditing by hand after each commit does not scale — it just moves the staleness.

Notably, `9bb8673` is the *best-defended* code reviewed in this audit: it arrived
with a written threat model, defense in depth, and its own test suite, and the
only real defects in it are two places where a stated invariant is not mechanically
enforced. That is the pattern that scales. The hand-audit is the part that does not.

Make the audit a gate rather than an event: run `tsc --noEmit`, the full suite,
`npm audit`, and `madge --circular` against a ref in CI, and fail the build on
regression. Everything in §0 was reproducible in 13 seconds and one sharded test
run — it belongs in a pipeline, not in a document.

### Operator notice carried forward from the previous change

A missing, unreadable, or unusable signing key **no longer degrades signing
silently — it fails the build outright.** As of this audit, a policy store that
cannot be reached **no longer grants a default policy — it returns 503.** Any
runbook written before 2026-08-03 describes a system that no longer exists.
